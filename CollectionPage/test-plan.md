## 1. 這份文件解決什麼問題

BDD 回答了「**使用者期待什麼行為**」，SDD 回答了「**系統如何實作這些行為**」。兩者之間有一道空隙：BDD 的 83 個展開案例是**可執行的期待**，但它們沒有指定「在哪一層驗證、用什麼工具、需要什麼資料、失敗時阻不阻擋發布」。

這道空隙就是 TDD 要填的：

- **BDD 的每個情境至少被一個測試案例承接**，且承接關係可被機器檢查（不靠人工聲稱）。
- **每項需求都有測試案例**，且能回答「這項需求若被改壞，哪個測試會紅」。
- **每個測試案例都指定層級**，避免把所有驗證都推給最慢最脆的 E2E。
- **測試資料是可複用的具名資料集**，不是散落在各測試裡的臨時物件。

## 2. 測試策略

### 2.1 五條策略原則

**原則一：能在此層驗證，就不要推給下一層。**
切換邏輯的方向判定、邊界回繞、資料驗證、時長計算，全部可以在無瀏覽器環境以純函式驗證。把它們留給 E2E，會讓回饋時間從毫秒變成分鐘，且失敗原因難以定位。本計畫因此有 **69 個單元案例（62%）**。

**原則二：E2E 只驗證「整合後才存在的東西」。**
焦點保留、真實動畫時長、實際版面位移、網路行為、縮放與觸控 —— 這些在單元層「假裝」驗證沒有意義。E2E 與 RWD 共 **26 個案例**，數量少但每個都不可替代。

**原則三：中斷與失敗路徑必須用可控時鐘驗證，不得使用真實計時器。**
FR-2.7 的中斷規格（連續快切、animationend 未觸發、舊計時器不得為新動畫收尾）若用真實 sleep 測試，會變成隨機紅燈的來源。本計畫以 `DS-J` 注入集搭配假時鐘驗證。

**原則四：資料契約在「建置期」驗證，而不是在「執行期」祈禱。**
FR-3.5 的證據強度、FR-3.6 的深度文案字數、FR-3.7 的替代文字、DR-1 的必填欄位 —— 這些全部在 `validate-projects.mjs` 以 ERROR／WARN 分級，並以結束碼阻擋發布（IT-14）。

**原則五：追溯關係要能被執行，而不是被宣稱。**
「83 個 BDD 案例都測到了」是一句很容易說、很難查證的話。本計畫把它變成 `validate-tdd.mjs` 的斷言：情境 ID 不存在、案例未對應需求、資料集代號打錯，全部會讓 CI 變紅。

### 2.2 測試層級劃分（依「驗證目的」而非「檔案位置」）

| 層級 | 驗證目的 | 一個案例通過的定義 | 執行環境 |
|---|---|---|---|
| 單元 | 單一模組的契約是否成立 | 純函式的輸入輸出關係成立；未使用真實 DOM／計時器／網路 | Node.js |
| 整合 | 模組協作後的資料流與事件流是否正確 | 呼叫序列、狀態落地順序與最終狀態正確；錯誤被正確吞掉或回報 | Node.js ＋ 替身 DOM ＋ 可控時鐘 |
| 端對端 | 真實使用者路徑在真實瀏覽器中是否可行 | 使用者可見結果正確；焦點、版面、網路行為符合契約 | Chromium |
| 響應式 | 尺寸、縮放、觸控與堆疊版面契約是否成立 | 在指定視窗／縮放條件下內容完整、可操作、順序正確 | Chromium ＋ 裝置模擬 |

### 2.4 測試金字塔與預算

```
                         ┌──────────────────┐
                         │  RWD      6      │  慢、脆、但不可替代
                         ├──────────────────┤
                         │  E2E     20      │  分鐘級；每案皆為使用者路徑
                         ├──────────────────┤
                         │  整合    16      │  秒級；模組協作與執行順序
                         ├──────────────────┤
                         │                  │
                         │  單元    69      │  毫秒級；回歸防護主力
                         │                  │
                         └──────────────────┘
   合計 111 個案例｜P0 88｜P1 21｜P2 2
```

**執行時間預算**：單元＋整合 < 10 秒（全案 85 個，必須能綁進編輯器存檔自動執行）；E2E＋RWD < 8 分鐘（含 4 個效能案例的 Lighthouse 執行）。

> 為什麼比例是 62% 單元而不是更高？因為這個系統的**核心價值集中在切換邏輯**，而切換邏輯的可測性極高（SDD 刻意把動畫計畫設計為純資料、把 store 設計為不持有 DOM）。可測性是架構決策的結果，不是測試的功勞 —— 這一點在 SDD ②③ 已鋪好。

## 3. 測試案例集

111 個案例的完整明細見：

- **`test-cases-unit.md`** — 69 個單元案例（依模組分組）
- **`test-cases-integration.md`** — 16 個整合案例
- **`test-cases-e2e.md`** — 20 個端對端案例
- **`test-cases-rwd.md`** — 6 個響應式與裝置案例

每個案例均具備七個欄位：**案例 ID、層級、標題、優先級、需求追溯、BDD 追溯、測試對象、前置條件、步驟、預期結果、工具、測試資料**。

### 3.1 案例 ID 命名規則

```
<層級前綴>-<模組>-<序號>
UT-STORE-07    單元測試   store.mjs    第 7 案
IT-01          整合測試                 第 1 案
E2E-14         端對端測試               第 14 案
RWD-03         響應式測試               第 3 案
```

層級前綴固定為 `UT` / `IT` / `E2E` / `RWD`，模組代號取自 SDD 的模組名（大寫）。序號在同一前綴內唯一。

### 3.2 優先級定義與 CI 行為

| 優先級 | 意義 | CI 行為 | 案例數 |
|---|---|---|---|
| **P0** | 阻斷發布。失敗代表使用者可見的功能錯誤、無障礙阻礙、或資料／隱私邊界破裂 | 阻擋合併；阻擋部署 | 88 |
| P1 | 高。失敗代表體驗瑕疵或特定環境下的問題 | 阻擋合併至主幹；可先部署至預覽環境 | 21 |
| P2 | 中。特定裝置或次要情境 | 需登錄追蹤；不阻擋 | 2 |

P0 佔 79% 是一個刻意的選擇：這個系統的功能面很窄（單頁、六件作品、一個切換機制），**窄系統的每一個行為都接近關鍵路徑**，因此沒有大量的「次要功能」可以降級為 P2。

### 3.3 代表性案例（節選）

**`UT-STORE-11` — clamp 模式：最後一件 next 抵達邊界**
> 前置：`count=6, currentIndex=5, orderMode=clamp`
> 步驟：`stepIndex(5, 6, +1, 'clamp')`
> 預期：回傳 null 或邊界訊號；`atBoundary.last` 為 true
> 追溯：FR-1.5 / `BAS-06`

這條案例揭露了一個 SDD 已實作的設計：FR-1.5 允許「循環」與「停用」兩種邊界規則，因此**兩種都必須有測試**，即使產品目前預設為 cycle。當產品決策改變時，切換設定即可，不需補測試。

**`UT-TRANS-11` — animationend 未觸發時保險清理仍執行**
> 前置：假時鐘；刻意不派送 animationend
> 步驟：`play()` 後推進假時鐘至 `min(duration,500) + 100ms`
> 預期：收尾仍發生；狀態不永久卡在 TRANSITIONING
> 追溯：FR-2.7 / `BP-08`

這是整個方案中最容易在真實環境翻車的一條：瀏覽器在分頁切到背景時會暫停動畫事件，導致依賴 `animationend` 的收尾永遠不執行，畫面卡在過場中間。**這條測試的價值不在於它會紅，而在於它讓「不依賴 animationend」這個規則無法被悄悄改壞。**

**`UT-ROUTER-07` — 還原期間抑制回寫以避免歷史迴圈**
> 前置：觸發 popstate
> 步驟：`popstate → show → 檢查是否再次 pushState`
> 預期：還原期間不回寫；不出現 popstate→show→pushState→popstate 迴圈
> 追溯：FR-1.6 / `BAS-13`

**`IT-01` — 四條進入路徑皆收斂至單一入口**
> 步驟：分別由 `next()`、`select()`、`setFilter()`、`resolveDeepLink` 觸發，記錄每次狀態落地所經過的函式
> 預期：四條路徑皆經過 `show()`；**不存在第二條改變當前作品的程式路徑**
> 追溯：FR-1.1／FR-1.2／FR-1.6／FR-1.7

SDD 的過程記錄顯示：初版 `store.step()` 自行更新 `currentId` 曾導致 8 項測試失敗。`IT-01` 就是那 8 項失敗的正式化 —— 它把「單一入口」從口號變成守門員。

**`IT-13` — 語意權杖對比符合 AA**
> 工具：沿用上游 `verify_contrast.py`
> 預期：一般文字 ≥ 4.5:1、大型文字 ≥ 3:1；零失敗
> 追溯：NFR-1.7 / `MA-19`

**`E2E-10` — 轉場不觸發版面重排且位移為零**
> 步驟：執行一次切換並錄影量測
> 預期：動畫僅使用 transform 與 opacity；累積版面位移分數 ≤ 0.1
> 追溯：FR-2.8／NFR-2.4 / `BP-05`

單元層的 `UT-TRANS-08` 已用 `assertCompositedOnly` 驗證**動畫計畫**只含合成屬性；`E2E-10` 驗證**真實版面**。兩者不是重複 —— 前者保證設計意圖，後者保證瀏覽器實際行為。

**`E2E-15` — 減少動態情境下功能與內容完全不減損**
> 前置：瀏覽器偏好設為減少動態
> 預期：不播放位移或縮放類動畫；可用淡入等非位移方式取代；**內容更新結果與一般模式一致**；切換、篩選與導覽功能全部可用
> 追溯：FR-2.3／FR-2.6／NFR-1.9

這條案例的判準刻意寫成「內容與功能一致」而非「沒有動畫」。前者是可驗證的行為契約，後者只是一個容易自我欺騙的觀察。

**`RWD-03` — 觸控目標尺寸足夠且間距足夠**
> 預期：主要控制項觸控目標 ≥ 24 × 24 CSS 像素；相鄰控制項間距足以避免誤觸
> 追溯：NFR-1.8 / `MA-20`

## 4. BDD → TDD 追溯

完整矩陣見 **`traceability-matrix.md`**（逐情境列出承接案例）。摘要：

| 指標 | 數值 | 狀態 |
|---|---|---|
| BDD 情境 | 72 | — |
| BDD 展開案例 | 83 | — |
| 承接的測試案例 | 111 | ✓ 每個情境皆 ≥ 1 個案例 |
| 需求項數 | 40 | — |
| 需求涵蓋 | 40 / 40 | ✓ 100% |
| 情境涵蓋 | 72 / 72 | ✓ 100% |

**追溯關係的三種形態（必須誠實說明，避免誇大其詞）**

1. **一對一**：多數情境由單一案例承接（例如 `BAS-05` → `UT-STORE-10`）。
2. **一對多（展開）**：Scenario Outline 的展開列由參數化案例承接。例如 `PH-04` 展開 5 列（五種證據強度），由 `UT-STORE-05`～`UT-STORE-07` 與 `DS-G` 的 8 個變體共同承接；`BAS-18` 展開 5 列（五種按鍵），由 `UT-KB-01`～`UT-KB-03` 涵蓋。
3. **多對一（收斂）**：多個情境由同一個整合案例承接。例如 `IT-01` 同時承接 `BAS-02`、`BAS-07`、`BAS-09`、`BAS-12`，因為「四條路徑收斂」本質上是一條橫跨四個情境的性質。

**為何是 111 而不是 83？** 因為測試案例集的範圍**大於** BDD 情境集：BDD 描述期待的行為（happy path 與主要例外），測試案例額外涵蓋**實作層的失敗路徑與環境注入**（假時鐘、pushState 拋錯、資料取得失敗、破圖、無效深連結、失效外部連結），以及 BDD 未涉及但 SDD 已定義的契約（權杖一致性、可合成屬性、排序穩定性、跳脫）。**83 是下限，不是上限。**

機器檢查：`node tools/validate-tdd.mjs` 會驗證每一個案例的需求 ID 與 BDD ID 都指向真實存在的項目，並計算涵蓋率。**任何一個情境失去承接案例，CI 立即變紅。**

## 5. 測試工具選用

### 5.1 選型原則

**原則一：執行期依賴維持 0 個。** SDD 的參考實作宣告 `package.json` 零 dependencies。測試工具屬於**開發期依賴**，不進入交付產物，因此不違反這個約束 —— 但也因此所有測試必須能在純 Node.js 下執行，不得引入需要編譯的原生模組。

**原則二：優先選「已內建」而非「功能更多」。** 單元與整合測試使用 Node.js 內建的 `node:test`，理由不只是省依賴：它讓 85 個快速案例**不需要任何安裝步驟即可執行**，降低「沒人跑測試」的風險。

**原則三：只在「非它不可」的層級引入重量級工具。** Playwright 進入 E2E 的唯一理由是：焦點行為、真實動畫時長、累積版面位移、網路節流，**沒有任何輕量替代方案能誠實驗證**。

### 5.2 工具對照表

| 用途 | 工具 | 涵蓋層級 | 理由與替代方案比較 |
|---|---|---|---|
| 單元／整合執行器 | **`node:test`**（Node.js 內建） | 單元、整合 | 零安裝、零依賴，支援子測試與 TAP 輸出。替代：Vitest（功能多但需建置管線）、Jest（需要 jsdom 與大量設定，且對 ESM 支援較繁瑣） |
| 斷言 | **`node:assert/strict`** | 單元、整合 | 內建。嚴格模式避免 `==` 弱比較掩蓋型別錯誤 |
| 假時鐘 | **`node:test` 內建 mock timers** | 單元、整合 | 中斷與保險清理測試的**必要條件**。若不控制時間，FR-2.7 的測試將無法穩定重現 |
| 行為替換（spy／stub） | 自製極簡替身（沿用 SDD 測試的替身 DOM） | 整合 | 只有 5 個替身需求（DOM、history、計時器、偏好查詢、資料取得），自製比引入測試框架的 mock 層更透明 |
| 端對端 | **Playwright** | E2E、RWD | 原生支援多瀏覽器、裝置模擬、網路節流、效能追蹤（`tracing`）、可存取名稱查詢。替代：Cypress（跨網域與多分頁較弱、無內建追蹤）、Selenium（設定成本高） |
| 無障礙檢測 | **`@axe-core/playwright`** | E2E | axe-core 是 WCAG 自動檢測的事實標準；與 Playwright 整合可對真實渲染結果檢測。**注意**：自動檢測抓不到約 30–40% 的無障礙問題，焦點順序與可理解性仍須人工 |
| 鍵盤與焦點驗證 | Playwright `keyboard` ＋ 自製焦點保留斷言 | E2E | 焦點保留是 FR-2.7 的可觀察結果，必須在真實瀏覽器驗證 |
| 效能量測 | **Lighthouse CI** ＋ Playwright 效能追蹤 | E2E、RWD | Lighthouse 提供行動裝置模擬與 LCP／CLS／TBT；Playwright 追蹤提供「長任務與版面位移是否由轉場引起」的因果證據 |
| 覆蓋率 | **`c8`**（V8 原生覆蓋率） | 單元、整合 | 讀取 V8 內建覆蓋率，不需原始碼instrumentation，對 ESM 支援良好。替代：nyc（基於 babel，對 ESM 較繁瑣） |
| BDD 執行 | **`@cucumber/cucumber`** | 整合 | 直接讀取 `.feature` 檔，讓 BDD 情境成為可執行規格。**本計畫僅定義 step definitions 的撰寫規範與範例，尚未完成全部 83 個案例的 step 實作**（見 §9） |
| 對比驗證 | 沿用上游 **`verify_contrast.py`** | 整合 | 已存在且已被上游驗證過（26/26 通過、抓到 2 個真實缺陷），不需重造 |
| 資料契約驗證 | 沿用 SDD 的 **`validate-projects.mjs`** | 整合 | 已實作 ERROR／WARN 分級與結束碼，直接接進 CI |
| 追溯驗證 | **`tools/validate-tdd.mjs`**（本計畫新增） | 全部 | 驗證需求與 BDD 涵蓋率、交叉參照完整性、案例與資料集唯一性 |

### 5.3 明確不採用的工具與理由

| 工具 | 不採用理由 |
|---|---|
| Jest | 需要 jsdom 才能測 DOM 相關邏輯，但本系統的核心邏輯**刻意設計為不觸碰 DOM**（純函式），引入 jsdom 只會製造「看起來像真實瀏覽器」的假象，實際上仍測不到版面與焦點 |
| Testing Library | 其價值在於「以使用者視角查詢 DOM」，但本計畫的 DOM 查詢需求集中在 E2E 層，而 E2E 已有 Playwright 的原生可存取查詢（`getByRole` 等），不需再引入一層 |
| Storybook＋互動測試 | 元件的組合方式單一（單頁六件），沒有元件展示與大量組合的維護需求 |
| 視覺回歸（Percy／BackstopJS） | 6 件作品、單一版面，視覺回歸的維護成本（基準圖更新審核）高於效益。改以 `E2E-10` 的位移量測與上游既有的對比驗證涵蓋視覺風險 |
| Mutation testing（StrykerJS） | **列為第二階段評估**而非不採用。它對「測試是否真的有效」的驗證價值很高，尤其針對 69 個單元案例；但首次導入成本較高，建議在核心模組穩定後針對 `store.mjs`、`transition.mjs` 試行 |

## 6. 測試環境與測試資料

### 6.1 環境矩陣

| 環境 | Node.js | 瀏覽器 | 用途 |
|---|---|---|---|
| 本機（開發者） | 20 LTS | Chromium | 單元與整合（存檔自動執行）；E2E 抽樣 |
| CI（每次推送） | 20 LTS | Chromium | 全部 111 個案例 |
| CI（每日夜間） | 20 LTS | Chromium ＋ WebKit ＋ Firefox | E2E 跨瀏覽器；Lighthouse 完整報告 |
| 發布前 | 20 LTS | Chromium（行動裝置模擬） | 全部 P0；效能預算閘門 |

**為何每日夜間才跑跨瀏覽器？** 跨瀏覽器是保真度最高的驗證，但也是回饋最慢的一層。把 Chromium 作為每次推送的守門員、其他引擎放在夜間，可以在「回饋速度」與「覆蓋廣度」之間取得平衡。

**支援基線**（承自 SDD ⑥）：Chromium 111+、Firefox 115+、Safari 16.4+。主要理由是這些版本皆支援 `:has()`、容器查詢、`@media (prefers-reduced-motion)` 的完整行為與原生 `dialog`。

### 6.2 測試資料集（`data/test-data.json`）

| 資料集 | 名稱 | 用途 | 承接案例數 |
|---|---|---|---|
| `DS-A` | 基準資料集（6 件，全欄位齊備） | 絕大多數案例的預設資料；對應 BDD Background 的 6 件假設 A3 | 96 |
| `DS-B` | 空資料集 | 0 件不崩潰（`BP-13`） | 2 |
| `DS-C` | 單件資料集 | 1 件時控制項停用、位置 1 / 1（`BP-12`） | 1 |
| `DS-D` | 排序與門檻資料集（12 件，order 刻意不依輸入順序） | 排序依 order（`PH-15`）、> 10 件啟用篩選（`BP-14`） | 2 |
| `DS-E` | 僅含必填欄位 | 選填欄位缺漏時省略區塊（`PH-09`／`BP-17`） | 2 |
| `DS-F` | 含致命缺陷 | ERROR 被丟棄、前台不崩潰（`PH-10`） | 3 |
| `DS-G` | 成果證據型別變體（5 型別 ＋ 3 違規） | FR-3.5 條件約束（`PH-04`） | 3 |
| `DS-H` | 受保密約束 | 隱私邊界（`FR-3.9`／`PH-13`） | 1 |
| `DS-I` | 失敗路徑注入（破圖／無效深連結／失效外連） | `BP-09`／`BP-10`／`BP-11` | 1 |
| `DS-J` | 時間與環境注入（假時鐘／拋錯／偏好變更） | 中斷、保險清理、降級 | 12 |

**資料設計的三個關鍵決定**

1. **`DS-D` 的 order 刻意不依輸入順序**（輸入順序為 30 / 10 / 20 / 40 …）。若順序恰好與 order 一致，排序缺陷會被掩蓋 —— 這正是「測試資料必須能失敗」的具體實踐。
2. **`DS-A` 中「互動體驗」分類恰好 2 件**，對應 BDD `BAS-09` 的假設。資料集刻意對齊 BDD 的前提，避免情境與資料脫節。
3. **`DS-G` 同時包含合規與違規變體**（8 個）。只測合規資料無法證明驗證器有效；必須同時餵入「measured 缺 source」「observed 帶未標來源數值」等違規樣本，才能證明條件約束真的在運作。

### 6.3 測試資料的維護規則

- 資料集定義在 `data/test-data.json`，**不得散落在測試檔中**。
- 新增作品的欄位若改變，須先更新資料集並重跑 `validate-tdd.mjs`。
- 所有字數門檻（摘要 80、深度文案 300–500）以**實際字元數**計算，不接受「看起來差不多」。

## 7. 覆蓋率目標

### 7.1 三種覆蓋率，不同標準

| 覆蓋率類型 | 目標 | 量測工具 | 說明 |
|---|---|---|---|
| **需求覆蓋率** | **100%（已達成 40/40）** | `validate-tdd.mjs` | 每一項 DR／FR／NFR 都有測試案例。這是**最高優先**的覆蓋率 —— 未測的需求就是未知的風險 |
| **BDD 情境覆蓋率** | **100%（已達成 72/72）** | `validate-tdd.mjs` | 每一個情境都有承接案例，且交叉參照可被機器驗證 |
| **行覆蓋率** | **≥ 90%** | `c8` | 針對純邏輯模組（`store.mjs`、`transition.mjs`、`router.mjs`、`view.mjs`、`tokens.mjs`） |
| **分支覆蓋率** | **≥ 85%** | `c8` | 條件分支（邊界模式、證據型別、降級路徑）必須被兩側走過 |
| **函式覆蓋率** | **≥ 95%** | `c8` | 未執行的函式代表測試與實作範圍脫節 |

**為何行覆蓋率只要求 90% 而非 100%？** 因為 DOM 操作與事件監聽的收尾路徑（例如 `removeEventListener` 的防禦分支）在替身環境中難以自然觸發，強行補測只會產生「為了覆蓋率而存在」的假測試。這些路徑交由 E2E 層驗證真實行為。

### 7.2 行覆蓋率的排除範圍（必須明確列出）

| 排除項目 | 理由 |
|---|---|
| `main.mjs` 的 `bootstrap` 啟動流程 | 啟動流程涉及真實瀏覽器 API，交由 E2E 涵蓋（`IT-11`／`IT-12` 則驗證其錯誤處理） |
| DOM 事件的實體派送與解除 | 替身 DOM 不模擬真實事件傳播；交由 E2E |
| `view.mjs` 的字串模板主體 | 模板的「長度」不是有效指標，其**欄位正確性**已由 `UT-VIEW-*` 逐欄位驗證 |

**這些排除必須寫進 `c8` 設定並附理由**，不接受無聲的排除 —— 未被記錄的排除等於隱藏的覆蓋率缺口。

### 7.3 覆蓋率之外的品質閘門

覆蓋率只回答「有沒有被執行」，不回答「有沒有被驗證」。因此本計畫另外設定三道具體的閘門：

1. **追溯完整性**：`validate-tdd.mjs` 必須 ERROR 0（需求 40/40、情境 72/72、交叉參照全部有效）。
2. **資料契約**：`validate-projects.mjs` 對示範資料 ERROR 0、WARN 0；對 `DS-F` 必須產生 ERROR 且結束碼為 1。
3. **對比契約**：`verify_contrast.py` 零失敗（一般文字 ≥ 4.5:1、大型文字 ≥ 3:1）。

**第二階段的建議閘門**：對 `store.mjs` 與 `transition.mjs` 導入突變測試，目標突變存活率 < 15%。這能回答「89 個單元案例是否真的在把關」這個覆蓋率無法回答的問題。

## 8. CI 流程

### 8.1 分階段執行（快速回饋優先）

```
┌─ 階段 0：靜態與契約（< 30 秒）──────────────────────────┐
│  · 語法檢查（10 個 .mjs）                              │
│  · 資料契約驗證 validate-projects.mjs                   │
│  · 追溯驗證 validate-tdd.mjs  ← 需求／情境涵蓋率閘門     │
│  · 權杖對比驗證 verify_contrast.py                      │
└────────────────────────────────────────────────────────┘
                        ↓ 全數通過才繼續
┌─ 階段 1：單元測試（< 10 秒，69 個案例）─────────────────┐
│  · c8 node --test                                      │
│  · 行覆蓋率 ≥ 90%、分支 ≥ 85%、函式 ≥ 95%              │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ 階段 2：整合測試（< 30 秒，16 個案例）─────────────────┐
│  · node --test（替身 DOM ＋ 假時鐘）                    │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ 階段 3：E2E ＋ RWD（< 8 分鐘，26 個案例）──────────────┐
│  · Playwright（Chromium）                               │
│  · axe-core 無障礙掃描                                  │
│  · Lighthouse CI 效能預算                               │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ 階段 4：跨瀏覽器（每日夜間）───────────────────────────┐
│  · WebKit ＋ Firefox                                    │
└────────────────────────────────────────────────────────┘
```

**階段 0 的設計意圖**：把「規格層的完整性」放在最前面，且執行成本最低。當某個需求失去測試案例時，30 秒內就會知道，不需要等 8 分鐘的 E2E 跑完。

### 8.2 閘門規則

| 情境 | 行為 |
|---|---|
| P0 案例失敗 | **阻擋合併、阻擋部署** |
| P1 案例失敗 | 阻擋合併至主幹；允許部署至預覽環境 |
| P2 案例失敗 | 記錄追蹤項目；不阻擋 |
| 需求／情境覆蓋率未達 100% | **阻擋合併**（階段 0，最優先） |
| 行覆蓋率低於目標 | 阻擋合併；但允許以「附理由的排除」調整 |
| 效能預算超標（LCP > 2.5s／CLS > 0.1） | 阻擋部署；警示合併 |
| 對比驗證失敗 | **阻擋合併**（NFR-1.7 為無障礙必要條件） |

### 8.3 失敗分級與處理時限

| 級別 | 定義 | 處理時限 | 處理方式 |
|---|---|---|---|
| **S1** | P0 案例失敗，且影響已部署版本 | **立即** | 回退部署；修復前凍結發布 |
| **S2** | P0 案例失敗，尚未部署 | 當次迭代 | 修復；不得以「跳過測試」方式繞過（見 §8.4） |
| **S3** | P1 案例失敗 | 當次迭代 | 修復或降級並記錄理由 |
| **S4** | P2 案例失敗 | 排入後續迭代 | 登錄追蹤項目 |

### 8.4 禁止事項（測試紀律的底線）

1. **禁止以 `skip`／`only` 讓失敗案例靜默通過。** 若確實需要暫時停用，必須標註對應的需求 ID 與到期日，並在 CI 輸出中列為警告。
2. **禁止為了讓測試通過而修改測試資料。** 資料集是契約的一部分；若資料正確而測試失敗，應修實作。
3. **禁止在 P0 案例中使用真實計時器。** 使用 `DS-J` 的假時鐘，違者視為 S2。
4. **禁止在斷言中使用「大於等於一個寬鬆下界」來規避時序問題。** 例如以「> 0ms」驗證轉場時長會讓 FR-2.2 的 150–400ms 區間失去意義。
5. **禁止未記錄的覆蓋率排除。** 排除必須出現在 `c8` 設定並附理由。

### 8.5 CI 產出物

- `c8` 覆蓋率報告（HTML ＋ lcov）
- Playwright 失敗截圖與影片（僅失敗案例）
- Lighthouse CI 報告（LCP／CLS／TBT，行動裝置模擬）
- `validate-tdd.mjs` 的涵蓋率摘要（貼在 PR 上，讓審查者一眼看到需求與情境涵蓋狀態）
- Playwright 效能追蹤檔案（供 `E2E-09`／`E2E-10` 的長任務與位移分析）

## 9. 誠實揭露的限制

**以下為本計畫的實際狀態，讀者不應從中推論出未發生的驗證。**

### 9.1 本計畫實際執行了什麼

- ✅ **追溯驗證已實際執行並通過**：`node tools/validate-tdd.mjs` → ERROR 0、WARN 1（31 個情境僅由單一案例涵蓋）、需求涵蓋 40/40、BDD 情境涵蓋 72/72、交叉參照全部有效。
- ✅ **案例文件由權威案例集渲染產出**（`render-cases.mjs`），因此文件與 JSON 不會分歧；並以 `check-artifacts.mjs` 驗証每個案例、每項需求、每個情境都實際出現在渲染文件中（10/10 通過）。
- ✅ **過程中抓到並修正了真實缺陷**：`UT-STORE-01` 將測試資料集代號誤寫為 `DS-DS-D`（驗證器立即判為 ERROR）；另發現驗證器自身的「步驟數 ≥ 2」規則過嚴，會誤判合法的單一呼叫型單元案例，已修正為 ≥ 1。

### 9.2 尚未發生的事（重要）

- ⚠️ **111 個測試案例目前是「規格」，不是「已實作的程式碼」。** 本交付產出的是案例定義、策略、資料與工具規範；將它們實作為可執行的測試檔（`*.test.mjs`、Playwright spec、step definitions）是下一步。**不應將本文件的案例數誤讀為已通過的測試數。**
- ⚠️ **BDD 的 83 個展開案例尚未全部實作為 step definitions。** 本計畫提供撰寫規範與範例（`ci/bdd-step-definitions.example.mjs`），但完整的 step 實作尚未完成。追溯矩陣證明「有案例承接」，不等於「step 已可執行」。
- ⚠️ **覆蓋率數字（90%／85%／95%）是目標，不是量測結果。** 因為測試尚未實作，`c8` 報告尚未產生。
- ⚠️ **效能案例（`E2E-19`／`E2E-20`）的判準來自公開文獻與 Core Web Vitals 建議值**，非本專案實測。LCP 2.5 秒與 CLS 0.1 是業界常用門檻，實際應以目標使用者的裝置與網路分布校準。
- ⚠️ **`E2E-17`（自動輪播的暫停控制）依賴一項尚未定案的功能決策。** SDD 記載自動輪播預設為 `false`；若產品決定不啟用，此案例應標記為 `skip` 並註明理由，而非刪除。
- ⚠️ **`UT-STORE-11`／`UT-STORE-20` 的 clamp 模式行為取決於另一項未定案的決策**（邊界規則採 cycle 或 clamp）。目前兩者皆有案例，是刻意的：決策改變時不需補測試。

### 9.3 已知的驗證盲區

| 盲區 | 影響 | 緩解方式 |
|---|---|---|
| **真實螢幕閱讀器未實測** | `IT-05`／`E2E-14` 只驗證 ARIA 屬性與可存取名稱，**無法驗證實際的朗讀體驗**（語速、重複朗讀、導覽節點是否合理） | 建議以 NVDA（Windows）與 VoiceOver（macOS／iOS）各進行一次人工走查 |
| **axe-core 僅能自動檢測約 60–70% 的無障礙問題** | 焦點順序的邏輯合理性、錯誤訊息的可用性、內容可理解性無法自動驗證 | `E2E-12` 的人工鍵盤走查 ＋ 建議的螢幕閱讀器走查 |
| **替代文字的「資訊量」無法自動判定** | `UT-STORE-09` 以規則啟發式檢查（長度、常見無資訊量字串），可能誤判或漏判 | 人工複審 `DS-A` 的 alt 欄位；規則僅作為第一道濾網 |
| **`prefers-reduced-motion` 的瀏覽器行為差異** | Playwright 的偏好模擬與真實作業系統設定可能有細微差異 | 建議在真實 macOS／Windows 系統設定下各做一次人工確認 |
| **單元層以替身 DOM 測試，非真實瀏覽器** | `mount` 相關行為、事件傳播、樣式計算的正確性無法在單元層保證 | 已由 `IT-*` 與 `E2E-*` 承接；SDD 亦已記載此限制 |
| **資料契約驗證只涵蓋「已定義的規則」** | 新型態的內容問題（例如新出現的誇大用語）不會被現有規則攔下 | FR-3.5 的證據強度模型是結構性防線；語言層面的誠實性仍需人工複審 |

### 9.4 本計畫刻意不處理的事

- **不驗證後端或資料來源的真實性**：本系統的資料為靜態 JSON，資料的「真實性」屬於內容治理，不是測試能解決的問題。
- **不驗證設計美感**：色彩、間距、字體的「好不好看」不在自動化測試的範圍。可程式化的部分（對比、位移、目標尺寸）已納入。
- **不涵蓋 SEO 與社群分享預覽**：這屬於另一份規格（`<title>`、`<meta>`、Open Graph）的範圍，本計畫未涉及。

### 10.2 執行方式

```bash
# 追溯與涵蓋率驗證（本計畫已執行，ERROR 0）
node tools/validate-tdd.mjs

# 重新渲染案例文件（修改 data/*.json 後執行）
node tools/render-cases.mjs

# 交付完整性檢查（文件與權威資料集是否逐案一致）
node tools/check-artifacts.mjs

# 後續實作完成後的實際測試（尚未實作）
cd ../portfolio-sdd/src && npm test          # 單元＋整合
npm run test:e2e                             # E2E＋RWD（Playwright）
npm run test:coverage                        # c8 覆蓋率報告
npm run validate                             # 資料契約驗證
```

### 10.3 建議的實作順序（給後續開發者）

1. **先寫階段 0 的 CI 閘門**（最小成本、最大效益）：讓追溯、資料契約、對比三道驗證先跑起來。
2. **再寫 69 個單元案例**：它們是回饋最快、最穩定的防護網，且能立刻驗證 SDD 的參考實作。
3. **接著寫 16 個整合案例**：需要建立替身 DOM 與假時鐘的共用測試工具；`IT-01` 與 `IT-02` 應最先完成，因為它們守護整個架構的核心。
4. **最後寫 26 個 E2E／RWD 案例**：需要真實頁面先存在。`E2E-12`（純鍵盤全流程）與 `E2E-15`（減少動態）建議優先，因為它們的失敗最難在後期補救。
5. **補齊 BDD step definitions**：以 `ci/bdd-step-definitions.example.mjs` 為範本，讓 83 個展開案例成為可執行規格。
